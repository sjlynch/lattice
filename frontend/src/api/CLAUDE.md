# frontend/src/api

Backend bindings, grouped by domain. `import { ... } from '../api'` resolves to `index.ts` here.

## Modules

- `types/` — domain-split shared API types (scan/health, settings, tasks, workflows, runs, git history, git setup). `types.ts` is a compatibility re-export shim.
- `http.ts` — `asJson<T>(r)` extracts `{error, code, detail}` from non-2xx responses so toasts get real messages, throwing a status-bearing `HttpError` (callers branch on `.status`, e.g. the workflow queue treating 409 as retry-able, or the Git Setup dialog treating 422 as "git doesn't know who you are"). `.detail` carries verbatim tool output the backend forwarded (git's stderr) — it must survive rather than being flattened into `.message`, because it is often the only place the fix is spelled out. `postJson`/`patchJson`/`deleteJson` centralize JSON request formation.
- `ws.ts` — `subscribeWs<T>(pathWithQuery, onMessage, onDisconnect?)`: auto-reconnecting WS (exponential backoff cap 5 s; backoff resets only after the socket survives `WS_STABLE_MS`; `onDisconnect` fires on every close, before the reconnect is scheduled). A frame is parsed inside a silent guard (malformed frames are dropped) but DISPATCHED outside it: a handler that throws is reported via `console.error('[ws] handler failed', path, err)` and never closes the socket. `subscribeWsShared` ref-counts one socket per path, parses each frame once and fans it out to every handler, with optional latest-snapshot replay for late joiners (used by `subscribeTasks`). Every WS subscriber builds on one of these.
- `ws.ts` also derives **backend connection health** from every `subscribeWs` socket (down from a close until it reopens; torn-down subscriptions never count): `isBackendConnectionDown()` / `subscribeBackendConnection(cb)`, behind the navbar's `BackendConnectionIndicator`. Never gates behaviour.
- `retry.ts` — `retryTransient(fn, {isCancelled?, onRetry?, retryIf?})`: retries a "start X" POST through a backend restart (fetch `TypeError`, 502 from vite's proxy, 503 e.g. `workflow-recovering`, 504) with 1→2→4→8→15 s backoff for up to 3 min; any other status is thrown at once. `mayHaveBeenApplied(err)` flags failures whose request may still have landed (network error, 504, a 502 that isn't ECONNREFUSED). Task Resume and workflow start pass `retryIf: err => !mayHaveBeenApplied(err)` and surface ambiguous acknowledgements without replaying: queue deduplication and active-run guards expire before transport retries do. Other callers retain their own retry/reconciliation policy.
- `scan.ts` — folder browsing + recursive source scan; git history/branch helpers, incl. `subscribeGitBranch(project, cb)` (the `/ws/git-branch` live navbar-chip stream — pushes the branch on connect + on every checkout) and `subscribeGitStatus(project, cb)` (the `/ws/git-status` stream — pushes a compact status signature on connect + whenever a commit/edit changes it, so the timeline scrubber can live-refresh `fetchGitHistory`, deduping on `GitHistoryResult.signature`).
- `health.ts` — `subscribeHealth(project, cb)`: the `/ws/health` `HealthUpdate` stream (one per file save / tree change).
- `settings.ts` — per-project `UserSettings` (`fetchUserSettings`/`patchUserSettings`) plus adjacent per-project/harness fetches: `subscribeHarnesses` (the `/ws/harnesses` availability stream), `getPiModels` (throws on a failed request — its callers keep their prior state rather than reading "no models") /`probePiEndpoint`, `ensureProjectInstrumentation`, `fetchProjectEnv`, `fetchInstructionTemplates`, `fetchHarnessSystemPrompts`.
- `globalSettings.ts` — machine-global settings (`maxConcurrentAgents`, MCP custom/override defs, `piModelMenu`, `piProviders`, `opengrep.packs`): `fetchGlobalSettings`, `patchGlobalSettings`.
- `opengrep.ts` — Opengrep (SAST) status / install / rule packs / scans: `fetchOpengrepStatus`, `startOpengrepInstall`, `installOpengrepRulePack`, `removeOpengrepRulePack`, `runOpengrepScan` (409 → `HttpError` with `.code` `busy` / `not-installed` / `no-rules`), `fetchOpengrepScans`, `fetchOpengrepDigest` (the markdown of a stored scan, `latest` by default). Backs Settings → Tools. `runOpengrepGraphScan(project, signal)` POSTs once with `async: true` and polls the accepted id with `format=graph` every 1.5 s. No automatic retries or startup scans; used only by the Security chip's click handler.
- `subscribeOpengrepStatus` shares successful engine status reads with the graph
  (latest-started request wins, aborted responses do not publish).
  `fetchOpengrepStatus` accepts an optional AbortSignal for lifecycle cleanup.
- `mcp.ts` — MCP control-plane: `fetchMcpCatalog`, redacted-secret get/set (`fetchMcpSecrets`/`setMcpSecret`), `fetchMcpEnvPresence`, `validateMcpServer`, and other-tool import `scanMcpImport`/`applyMcpImport`. Raw secret values never cross this boundary.
- `tasks.ts` — task CRUD + `runTask`, `resumeTask`, `mergeTask`, `subscribeTasks`. Every by-id call (`updateTask`, `deleteTask`, `runTask`, `resumeTask`, `cancelQueuedRun`, `mergeTask`, `abortTaskMerge`) takes the ACTIVE board's project first and sends it as `?project=` via `taskByIdUrl`, so the backend's `requireTaskInRequestedProject` pin 404s a task from another board (the id lookup is otherwise global). Pass the board's `activeFolder`, never the task's own `projectPath` (that makes the check vacuous); a 404 surfaces through the caller's normal `showError` path.
- `mergeRuns.ts` — `startMergeRun`, `getActiveMergeRun`, `cancelMergeRun`, `subscribeMergeRuns`.
- `workflows.ts` — workflow CRUD + `startWorkflow`, `fetchWorkflowRun(project, runId)` (one run by id incl. a recently finished one; `null` on 404, throws otherwise), prompt-customization start/status helpers, `subscribeWorkflows`, `subscribeWorkflowRuns`. `updateWorkflow`, `deleteWorkflow` and `cancelWorkflowRun` take the ACTIVE project first and send it as `?project=` (`withProjectParam`, the workflow twin of `taskByIdUrl`; empty project → no param = unpinned), so the backend 404s a workflow / run from another project. Pinned by `__tests__/workflowByIdProjectPin.test.ts`.
- `pushRuns.ts` — push-run lifecycle (commit + push the project via a Claude session): `checkGit`, `startPushRun`, `fetchPushRunStatus`, `forgetPushRun`. `checkGit` returns both `hasGit` (plain `fs.stat` of `<path>/.git`, what the Push button reads — do NOT make it walk up) and the additive `git: ProjectGitProbe` behind the Git Setup chip (which does walk up, so it can report `nested`). Treat `git` as possibly-absent at runtime; an older backend still answers the route.
- `projectInit.ts` — Git Setup: `previewProjectInit(project, gitignore?)` (what a first commit would capture; re-POSTed debounced as the user edits the `.gitignore`) and `initProjectGit(project, gitignore?)`. `initProjectGit` throws an `HttpError`; the dialog branches on `.status === 422` and renders `.detail` — git's own stderr, which is the only place the fix commands appear (the backend is barred by a guard test from naming those config keys).
- `qaRuns.ts` — QA e2e-run lifecycle (Playwright Claude over one merged task; mirrors `pushRuns`): `startQaRun`, `fetchQaRunStatus`, `forgetQaRun`.
- `postMergeHooks.ts` — post-merge hook run state: `getActivePostMergeHook`, `abortPostMergeHook`, `subscribePostMergeHooks`.
- `terminals.ts` — `subscribeTerminalActivity(project, cb)`: the `/ws/terminal-activity` stream of backend session ids whose harness is still working, behind the sidebar's per-tab spinner. Payload is machine-wide (`busy: serverId[]`), so the consumer intersects it with its own project-scoped tab list. Not to be confused with `../terminal/terminalApi.ts`, which holds the pty create/DELETE side effects. Also `fetchTerminalServerStatus()` (`GET /api/terminal-server/status`: is the detached executor `stale`, and how many sessions its deferred update waits on) behind the navbar's `TerminalServerChip`.
- `terminalTabs.ts` — the durable terminal-tab registry (`/api/terminal-tabs`, `/ws/terminal-tabs`; `backend/src/terminalRegistry/`): `fetchTerminalTabs(project)` (the project's records — throws on a non-2xx, so a mid-restart backend reads as "unknown", never "no tabs"), `restoreTerminalTabs(project, {retry?})` (the on-open / "Restore tabs" pass → `RestoreSummary`; `retry` also retries tabs whose earlier relaunch failed), `patchTerminalTabLabel(project, id, label)` / `patchTerminalTabOrder(project, order)` (decorations), `closeTerminalTab(project, id, callbacks?)` (`void`, not an awaitable Promise; optional `onClosed`/`onError` callbacks signal confirmation/failure: 404 means already closed, `{ok:true}` confirms success; other HTTP/transport/unconfirmed responses reach `onError`, or log a warning without callbacks. DELETE persists close intent before attempting kill; an uncertain kill retains registry/PTY ownership and returns retryable 503 `terminal-close-unconfirmed` — close intent is not proof the PTY is gone. Registered closes use this helper through `useTerminalActions`, keeping the tab until confirmation and providing explicit retry feedback on failure; the unregistered `deleteBackendSession` fallback remains best-effort. Full lifecycle: [frontend/src/terminal/CLAUDE.md](../terminal/CLAUDE.md) and [backend/src/terminalRegistry/CLAUDE.md](../../../backend/src/terminalRegistry/CLAUDE.md)), and `subscribeTerminalTabs(project, cb)` (the `hello` / `upsert` / `ended` / `removed` / `restored` / `restore-failed` / `restore-summary` stream). Records are CREATED by the backend at pty creation; the frontend only reads, restores and decorates. Consumed by `../TerminalsContext.tsx` and `../terminal/terminalRegistrySync.ts`.

## Adding an endpoint

`subscribeWsShared` accepts optional per-subscriber `onDisconnect` callbacks
and a `resetReplayOnDisconnect` channel policy. Terminal activity opts in so a
lost connection cannot replay stale busy ids; ordinary snapshot feeds keep their
existing replay behavior. Callers sharing a path must use the same replay policy.
Each subscription owns a separate registration even when callbacks are reused;
cleanup is bound to that channel instance. Message, disconnect, and immediate
replay callback failures are isolated from other subscribers and cleanup.

1. Type goes in the matching `types/<domain>.ts` file, and is re-exported by `types/index.ts`.
2. Function goes in the matching domain file. Use `asJson` for simple GETs and `postJson`/`patchJson`/`deleteJson` for JSON writes.
3. WS endpoints: call `subscribeWs(path, cb)` (or `subscribeWsShared` when several features watch the same path) — don't reinvent reconnect/backoff.
4. New domains: add a file + add `export *` to `index.ts`.

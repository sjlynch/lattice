# backend/src

Express server (`:5184`) plus a detached PTY subprocess on `:5185`.

## Layout

- `index.ts` — entry point. Installs `processGuards` first, then dynamically imports `server/startup.ts`.
- `server/` — backend bootstrap helpers: config/default root, Express app + route mounting + JSON error middleware, HTTP/WS server wiring, and startup ordering (`ensureTerminalServer` + `recoverOrphanedTasks` before listen, `resumeInterruptedMergeRuns` after listen).
- `recovery.ts` / `recovery/` — `recovery.ts` is the stable public shim; focused modules under `recovery/` handle boot recovery: restore tasks.json from backup → restore orphan working-tree snapshots → **`sweepOrphanedWorktrees`** (reclaim worktrees git tracks that no live task owns) → recover ready_to_merge tasks whose branch was deleted. Also exports **`resumeInterruptedWorkflowRuns(backendOrigin)`** (`recovery/workflowRunResume.ts`) — the same problem one level up: a *workflow* run is in-memory too, and `dev.mjs` defers a restart only while a `run.lock` is held (control steps), so a restart during a long **agent** step used to erase the run outright — the navbar chip vanished and the still-running agent's `/complete` landed on a backend that had never heard of the run, so every remaining step silently never ran. Runs are now mirrored to `~/.lattice/per-project/<hash>/workflow-runs.json` (`workflowRuns/persistence.ts`) and re-adopted here: a live agent pty (they survive in the detached terminal-server) is re-attached, a killed control step is re-dispatched, a dead agent session errors the run instead of hanging. Called *before* the merge-run resume, which then skips any project with an active workflow run. And **`resumeInterruptedMergeRuns(backendOrigin)`** (called from `server/startup.ts` *after* `listen`): a merge run executes in the backend process, so `tsc -w` + the dev restart loop will kill it whenever a merged task fast-forwards `main` with a `backend/src` change (or the run's working-tree snapshot churns an uncommitted `.ts` file) — this spots the stale `merge-run` `run.lock` that leaves behind and starts a fresh run for the remaining `ready_to_merge` tasks (idempotent on partial states). The dev runner *also* tries to avoid the restart in the first place (`scripts/dev.mjs` defers a restart while a `run.lock` is held); this is the backstop for when one happens anyway (or a real crash).
- `routes/` — one router per domain (health, search, settings, globalSettings,
  mcp, terminals, tasks, agentActivity, projectClaude, mergeRuns,
  postMergeHooks, pushRuns, qaRuns, workflows). Each is a `buildXRouter()`
  factory and is mounted from `server/app.ts`; see `routes/CLAUDE.md` for the
  route map.
- `ws/` — single `upgrade` dispatcher in `wsServer.ts`, generic project-scoped helpers in `projectEndpoint.ts`, and endpoint-specific WSS factories under `ws/endpoints/`. Adding a WS endpoint = add an endpoint builder plus a route in `attachWebSockets`.
- `worktree/` — git-worktree subsystem (see its `CLAUDE.md`). The `worktree.ts` shim re-exports the public surface. Includes `projectGit` (whitelisted git wrapper for the project repo) and `gitBackup` (`git bundle` pre-run backup).
- `homeScratch/` — the canonical home-scoped-scratch contract shared by `pushRuns/` / `qaRuns/` / `postMergeHooks/`: the `.git`-deletion **path guard** (`createHomeScratchPaths` → `assertSafeSessionPath`), the **session-setup builder** (`setupHomeScratchSession` / `startHomeScratchAgentSession`: mkdir scratch + Claude trust + completion/activity hooks + brief render + queued pty pre-spawn + presence registration), and the **bounded recursive cleanup** (`cleanupHomeScratchSession`). Each run-type's `paths.ts`/`session.ts`/`cleanup.ts` are thin wrappers passing a `{dirName, idPrefix, logLabel, noun}` config. See its `CLAUDE.md`. **Path-guard / cleanup changes go here, not in the per-feature dirs.**
- `pushRuns.ts` / `pushRuns/` — one-off Claude sessions for the QA-lane Push button. Session scratch lives at `~/.lattice/per-project/<hash>/push/<id>/` (not `<project>/.lattice/`) and cleanup is guarded so recursive removal only targets that home-scoped root. Path/setup/cleanup are now delegated to `homeScratch/`.
- `postMergeHooks.ts` / `postMergeHooks/` — optional per-project post-merge hook: after a merge, spawn the configured harness with the user's prompt and gate merge completion on its callback. Same scratch / Stop-hook / registry-waiter shape as `pushRuns/`, scratch at `~/.lattice/per-project/<hash>/post-merge-hooks/<id>/`. See its `CLAUDE.md`.
- `qaRuns.ts` / `qaRuns/` — QA-lane "run an end-to-end test" sessions, surfaced per task (and lane-wide) when the QA-lane `qaPlaywright.enabled` toggle is on. A one-off Claude session spawns from home-scoped scratch (`~/.lattice/per-project/<hash>/qa/<id>/`, **outside** the repo) with `projectPath` set **and `isQaRun: true`** so `effectiveMcpServers` injects the QA-scoped Playwright MCP (with the QA lane's headed/headless choice — the only spawn that resolves `qaPlaywright`); the brief (`QA_INSTRUCTIONS.md`) has the agent `cd` into the project, drive the merged feature end-to-end with the Playwright browser tools, append a human-readable PASS/FAIL verdict to the task via `/append-summary`, then post a *structured* verdict to `POST /api/qa-runs/:id/verdict` (`{verdict, confidence}`) before stopping. `qaRuns/verdict.ts` (`applyQaVerdict`) records that verdict on the run and, on a **confident PASS** (`verdict:"pass"` + `confidence:"high"`), auto-advances the task `qa → done` (guarded: only when the task is still in the `qa` lane); a FAIL or an unsure PASS leaves it for a human. The verdict is reported *before* the session stops, so it lands while the run is still tracked. The qa → done transition has **two triggers** (mirroring how in_progress → ready_to_merge fires from the model's explicit curl AND the reliable Stop hook / Pi completion extension, so it never hinges on the model remembering): the agent's explicit `/verdict` curl (fast path) and a **`/done` Stop-hook backstop** (`applyRecordedQaVerdict`) that re-applies whatever verdict was recorded — both idempotent via `promoteOnConfidentPass`, so the move lands even if the explicit curl never did (it failed / was forgotten / raced `/done`). A stop with no recorded verdict stays in QA for a human (the Stop hook can't synthesize a pass/fail). So `/done` is **no longer pure cleanup** — it is the QA analogue of the Claude Stop hook / Pi extension closing the lane. Near-clone of `pushRuns/` (registry / paths / Stop-hook / cleanup / boot-sweep), so the same `.git`-safe guards apply. Served by `routes/qaRuns.ts` (`POST /api/qa-runs {project, taskId}`, `GET`/`POST :id/verdict`/`POST :id/done`/`DELETE :id`). **Do not set `taskId` on its terminal** — a QA task is already in the `qa` lane, and `useTaskTerminalCleanup` closes every terminal tagged with a qa/done/deleted task.
- `projectPath.ts` — `canonicalProjectPath`, `projectHash`, `latticeHomeDir`, `homeProjectDir`, `homeProjectScratchDir`, `homeWorktreesDir` — the single source of truth for per-project paths under `~/.lattice/`.
- `search.ts` / `ripgrep.ts` — file-*contents* search backing `/api/search` (the graph search bar's contents pass). `search.ts` orchestrates: try the `ripgrep.ts` fast-path (detected once, memoized; restricts to `SOURCE_EXTS` minus `IGNORE_DIR_NAMES`, honoring `.gitignore`), else a concurrency-limited Node read loop. Wildcard `*`/`?` translation in `regexSource` is kept in sync with the frontend's `searchMatcher.ts`. Returned paths are absolute == graph file-node ids.
- `fsbrowse.ts` / `fsbrowse/` — folder-picker backend: public shim plus roots, validation, listing, and create-directory helpers.
- `gitHistory.ts` / `gitHistory/` — one `git log --name-status -M` round-trip backing the timeline scrubber (`GET /api/git-history`); splits git execution (`index.ts`, `clampLogLimit` 1–50) from pure parsing (renames → delete+add, porcelain `-z`). Also returns a compact `signature` (`gitHistory/signature.ts` — `git status --porcelain=v2 --branch -z` hashed; HEAD + dirty set) the frontend dedupes the `/ws/git-status` live refresh against. See its `CLAUDE.md`.
- `gitBranch.ts` — `getCurrentBranch(repoRoot)` (the navbar branch label, shared by `routes/health/gitInfo.ts`'s `/api/git-branch`) plus `subscribeGitBranch(projectRoot, cb)`: a lazy per-project **read-only** chokidar watcher on `.git/HEAD` that re-derives the branch and fans it out to subscribers whenever HEAD changes (a `git checkout`). HEAD moves only on checkout/detach — a plain `commit` advances the branch ref, not HEAD — so it's a precise, low-noise signal. Backs `/ws/git-branch` (`ws/endpoints/gitBranch.ts`) so the navbar chip updates live. Watch-only, no writes/deletes ⇒ irrelevant to the `.git`-deletion defences.
- `gitStatus.ts` — `subscribeGitStatus(projectRoot, cb)`: lazy per-project **read-only** chokidar watcher backing `/ws/git-status` (`ws/endpoints/gitStatus.ts`) so the timeline scrubber stops going stale after a commit / working-tree edit (it used to fetch `/api/git-history` once per project and only refresh on a full page reload). Watches the repo's git-metadata dir (minus `objects`/`lfs`) **and** the working tree (gitignore-aware, `.git` excluded), and on any debounced change recomputes the `computeStatusSignature` (shared with the endpoint) — waking subscribers only when it actually changed. Two watchers per opened project, event-driven (no polling). `computeStatusSignature` never rejects (a vanished project cwd would otherwise unhandled-reject → process-guard fail-fast). Watch-only ⇒ irrelevant to the `.git`-deletion defences. Sibling of `gitBranch.ts`; regression-covered by `__tests__/gitStatus.test.ts`.
- `projectRunLock.ts` / `projectRunLock/` — cross-process per-project lock (`~/.lattice/per-project/<hash>/run.lock` = `{pid, hostname, startedAt, label}`, PID-liveness probe). Held for the duration of a merge run (`label: merge-run`) / manual `/merge` (`label: manual-merge`). The in-process guards (mergeRuns singleton, `mergeLocks`) don't see other Lattice processes; this does. `inspectProjectRunLock` reads it without acquiring — used by recovery's merge-run resume to spot an interrupted merge run, and by `scripts/dev.mjs` to know when to defer a restart. `projectRunLock.ts` is the public facade; the subfolder splits path construction, lockfile parsing, liveness checks, stale-lock stealing, acquisition, and release helpers.
- `tasks.ts` / `taskCache.ts` / `taskCache/` — `tasks.ts` and `taskCache.ts` are stable re-export shims; implementation lives in `taskCache/` (see its `CLAUDE.md`). It owns the in-memory per-project task cache, 100 ms debounced persistence, home-dir storage under `~/.lattice/per-project/<sha1(canonical-path)[:12]>/tasks.json`, `~/.lattice/projects.json` indexing, legacy in-project migration, and crash-safe updates that write disk before mutating cache.
- `workflows.ts` / `workflows/` — workflow definitions facade plus split types, normalization, `interpolate.ts`, and `WorkflowStore`. Uses `ProjectStateManager` while preserving `<project>/.lattice/workflows.json`, step normalization, and `(projectPath, workflows)` subscriber fan-out. Every workflow carries a `variables` array; normalization guarantees the built-in `user_instructions` variable is always present (`ensureUserInstructions`). `interpolate.ts`'s `interpolateWorkflowVariables` substitutes `{{name}}` references in a step prompt with the workflow's variable values (called from `workflowRuns/stepMarkdown.ts` before the prompt reaches the agent); unknown refs are left intact so typos stay visible.
- `harnesses.ts` — shared backend vocabulary/helpers for agent harness strings (`claude` / `pi` / `codex`). Reuse this instead of open-coding harness unions or normalization. Also `agentHarnessForCommand(command)` — which harness (if any) a shell command launches, for the places that only have the command string (`terminalActivity.ts`); leading-token only, tolerant of quotes/paths/`.cmd` shims.
- `terminalActivity.ts` — the "is the agent in this terminal still working?" signal behind the sidebar's per-tab spinner (`/ws/terminal-activity`, `ws/endpoints/terminalActivity.ts`). The ptys live in the detached terminal-server with no event channel back here, so this **polls** `proxyListSessionsOrNull()` (~1s) while ≥1 client is subscribed and fans out the busy set **only when it changes** — with N agents working the poll result is identical tick after tick, and broadcasting each one would re-render every sidebar tab. A `null` probe is "can't tell" and holds the last set rather than blinking every spinner off during a terminal-server restart. The terminal-server records only raw facts (`Session.lastOutputAt`, `Session.initialCommand` → `listSessions`); the POLICY — the idle threshold (`TERMINAL_BUSY_IDLE_MS`) and the agent-vs-plain-shell test — lives here on purpose, so tuning it is a main-backend edit that doesn't change the terminal-server fingerprint and respawn every running pty. Output recency is a deliberate heuristic: all three harnesses animate a status line while working and go quiet at their prompt, and it's the only signal that covers Codex/Pi (which have no activity hooks) *and* tabs whose `TerminalPane` was never mounted. `computeBusyTerminalIds` is the pure core (tested in `__tests__/terminalActivity.test.ts`).
- `harnessSystemPrompts.ts` / `harnessSystemPrompts/` — per-project, per-harness overrides of the AGENT'S OWN built-in system prompt (Append and/or Replace), distinct from the Lattice-authored briefs in `instructionTemplates/`. `harnessSystemPrompts.ts` is the public barrel; the subfolder holds the leaf catalog (`defs.ts`), the resolver (`resolve.ts`), the settings-editor payload (`editorData.ts` → `GET /api/harness-system-prompts`), the Pi `before_agent_start` extension shim (`piShim.ts`), and the per-harness injectors (`inject.ts`). Resolved + applied at the single spawn chokepoint (`terminalServerClient/createSession.ts` `resolveHarnessSpawnBody`): Claude scratch-file + `--(append-)system-prompt-file` flag (applied in the terminal-server), Codex `developer_instructions`/`model_instructions_file` `-c` overrides, Pi a cwd-local extension (like the MCP shim). Stored on `UserSettings.harnessSystemPrompts`. See its `CLAUDE.md`.
- `harnessDetect.ts` — lazily probes which agent CLIs (`claude`/`pi`/`codex`) are on PATH (memoized; `resetHarnessCache()` re-probes). Drives the UI's `/ws/harnesses` availability push.
- `piModels.ts` / `piModels/` — `piModels.ts` is a re-export barrel; the implementation is split under `piModels/` by concern: `discovery.ts` (the read side — `pi --list-models` parsing/caching + menu curation), `reconcile.ts` (the write side — `reconcilePiModelsJson`, models.json sync), `probe.ts` (the write side — `probeEndpointModels`, "Detect models"), and `config.ts` (the one `PI_MODELS_CONFIG` object grouping the timeout/TTL knobs + the shared `~/.pi/agent` path). Existing `./piModels.js` import paths keep working unchanged. The `pi --list-models` spawn and `piSubagents.ts`'s `pi install` spawn share `spawnWithTimeout.ts` (spawn + capture stdout/stderr + kill-on-timeout, resolving a structured result). Pi model discovery for the harness dropdowns: `getPiModels(curated?)` shells `pi --list-models` (output is on **stderr**; memoized w/ short TTL + `resetPiModelsCache()`), parses the fixed-width table (`parsePiListModels`, tested), reads `~/.pi/agent/models.json` (custom providers + friendly names) and `settings.json` (`defaultProvider`/`defaultModel`) read-only, and returns `{models, menu, defaultPattern}` — `menu` is `globalSettings.piModelMenu` if set, else the default (custom-provider models + Pi default). `normalizePiModel` (re-exported from `worktree/commands.ts`) + `resolvePiModel(projectPath)` (reads `UserSettings.piModel`) back the per-spawn model resolution. **Endpoint management:** `reconcilePiModelsJson()` upserts `globalSettings.piProviders` into `~/.pi/agent/models.json` (atomic temp+rename, preserves hand-written providers + a re-managed id's `compat`/`headers`, tracks managed ids in the `~/.lattice/piManagedProviders.json` sidecar so a UI removal is a precise delete) and `probeEndpointModels(baseUrl, apiKey?)` GETs `<baseUrl>/models` for the "Detect models" button. **Every managed provider always gets an `apiKey`** (defaults to `"local"` when blank): Pi *requires* one on any custom provider that defines models, and a single keyless provider makes Pi reject the WHOLE models.json — taking the user's hand-written providers down with it. The curated `menu` therefore also treats a models.json-declared pattern as valid even when `pi --list-models` doesn't report it (that CLI drops every custom provider if any one is malformed), so curation isn't silently hidden. Reconcile runs on boot (`server/startup.ts`) + after a global-settings PATCH carrying `piProviders` (`routes/globalSettings.ts`). Served by `routes/settings.ts` (`GET /api/pi-models`, `POST /api/pi-endpoints/probe`). Selection stays per-spawn via `--model` (`worktree/commands.ts` `buildPiModelFlag`); `~/.pi/agent/settings.json` is never touched.
- `piSubagents.ts` / `piSubagents/` — `piSubagents.ts` is a re-export barrel; the implementation is split under `piSubagents/` by concern: `paths.ts` (install dir + package-entry resolution), `install.ts` (the `pi install … -l` spawn), `ensure.ts` (single-flight install state), `render.ts` (pure shim rendering + filename), `shim.ts` (writing the shim into a session cwd). Existing `./piSubagents.js` import paths keep working unchanged. See `piSubagents/CLAUDE.md`. Auto-installs the `@tintinweb/pi-subagents` Pi extension into a shared Lattice-owned dir (`~/.lattice/pi-extensions/` via `pi install … -l`, so the user's global `~/.pi/agent/settings.json` stays `packages: []`) and drops a re-export *shim* `.pi/extensions/lattice-subagents.ts` (`export { default } from "<shared entry>"`) wherever Lattice already drops `lattice-complete.ts` (worktrees, workflow steps, post-merge, prompt-customization) **plus the project root** — Pi extension discovery is cwd-exact (no walk-up), so the project-root shim is the only way to reach a `pi` the user types in the Lattice terminal panel. `ensurePiSubagentsInstalled()` (boot + project open, idempotent/single-flight, never throws) resolves the entry; `installPiSubagentsShim({dir})` is a graceful no-op until then. The shim coexists with `lattice-complete.ts` and is gitignored/excluded via `worktree/managedFiles.ts`.
- `piMcp.ts` / `piMcp/` — the Pi MCP loader (see `piMcp/CLAUDE.md`). Near-clone of `piSubagents/` for the third-party `pi-mcp-adapter` (official Pi ≥0.74): private shared install under `~/.lattice/pi-mcp-adapter/` + a cwd-exact loader shim, plus a per-cwd `<cwd>/.pi/mcp.json` writer (marker-reconciled). Unlike Claude/Codex, Pi's config is cwd-local files the adapter auto-discovers, so the **backend** writes them at the spawn chokepoint (`applyPiMcpForSpawn` in `terminalServerClient/createSession.ts`), shipping only the secret env to the pty. Each server carries `lifecycle: 'eager'` + `directTools: true`; HTTP-header secrets ride `${VAR}` refs (value in pty env), lifting the old `pi-mcp-extension` limitation. Config shaping is in `mcp/piServerConfig.ts`; resolution in `mcp/registry.ts` (`resolvePiServers` / `resolveManagedPiServers`).
- `mcp/` — the MCP control plane (see its `CLAUDE.md`): code catalog of built-in servers, the harness-neutral `resolveMcpEntries` core + per-harness shapers/resolvers (`resolveManagedClaudeServers` → `~/.claude.json`, `resolveManagedCodexServers` → `-c` inline-TOML overrides in `terminal/codexTrust.ts`, `resolveManagedPiServers` → `piMcp/`), the `0600` secrets file, the reconcile/win32-wrap shaping for Claude's `mcpServers`, key validators, and config import. **Per-harness toggles**: Claude uses `UserSettings.mcpOverrides`, Codex/Pi use `mcpHarnessOverrides` — three independent switches per server, all off by default. **Policy is resolved in the main backend and applied by the terminal-server** (split so the detached terminal-server never imports the resolver — a policy edit is then backend-only and never forces an agent-killing respawn). Per-spawn: `proxyCreateSession` (`terminalServerClient.ts`) resolves the managed set + memory opt-out and ships them in the `POST /sessions` body; the terminal-server calls `applyClaudeProjectConfig(cwd, { managed })` (`claudeTrust.ts`) microseconds before spawn. Also persisted into the user's own `projects[projectRoot]` entry by `routes/projectClaude.ts` on project open / settings save (so global servers reach sidebar + hand-started `claude` sessions). Served by `routes/mcp.ts`. Definitions live in `globalSettings.json` (`mcpCustomServers`/`mcpBuiltinOverrides`); per-project enables in `userSettings.json` — `mcpOverrides` (per-server global toggles, incl. `mcpOverrides.playwright`) and `qaPlaywright` (the QA lane's separate QA-runs-only Playwright + headed/headless switch).
- `claudeTrust.ts` / `claudeTrust/` + `claudeConfigGuard.ts` — write `~/.claude.json` so Lattice-spawned Claude sessions skip the "trust this folder" dialog and pick up the backend-resolved MCP set (the apply side of the MCP control plane). `claudeTrust.ts` is a stable facade over `claudeTrust/` (see its `CLAUDE.md`): `apply.ts` (the trust + MCP-reconcile write path — apply mechanism only, no policy resolution), `configFile.ts` (the `~/.claude.json` I/O primitives: heal-on-read, atomic temp→rename `atomicWriteFile`, restore-from-backup), `configLock.ts` (the mkdir config mutex), `maintenance.ts` (boot/timer sweeps: prune dead ephemeral `projects[<cwd>]` entries + reclaim orphaned `.lattice-*.tmp`), `util.ts`. `claudeConfigGuard.ts` is the slower boot/periodic/post-kill backstop layered on the same primitives. The whole `claudeTrust/` subtree is in the terminal-server fingerprint (`terminalFingerprint.ts`) — see `mcp/CLAUDE.md` "Injection sites".
- `workflowPromptCustomizations.ts` / `workflowPromptCustomizations/` — public shim plus focused modules for `.lattice/workflow-prompt-customizations/<id>/` sessions: request types/registry, scratch paths, instruction + submit-script rendering, selected-harness command/session startup, and completion callback handling.
- `mergeRuns.ts` + `mergeRuns/` / `workflowRuns.ts` + `workflowRuns/` — sequential run engines. `mergeRuns/` holds state/preflight/per-target helpers (see its `CLAUDE.md`); the public singleton + worker loop stay in `mergeRuns.ts`. `mergeRuns` also: takes a `git bundle` backup pre-run, holds the cross-process run lock, and runs a circuit-breaker (`.git`-exists + HEAD-only-forward) between tasks that halts the whole run on a violation. Singleton WS subscribers (`subscribe`) for live event fan-out. The run lives in-process, so a backend restart kills it — but it's written to be safely **re-runnable**: `startMergeRun` re-scans `ready_to_merge` (incl. conflict-flagged) tasks and re-attempts each, and a half-done task (worktree merged but `main` not FF'd, finalize interrupted, …) is idempotent on retry. `recovery.ts`'s `resumeInterruptedMergeRuns` leans on this. `workflowRuns.ts` is a thin facade over the `workflowRuns/` submodules — see its `CLAUDE.md`.
- `globalSettings.ts` — machine-global settings at `~/.lattice/globalSettings.json` (distinct from per-project `userSettings.ts`): `maxConcurrentAgents` (the spawn queue's `softCap`), MCP custom-server defs / built-in overrides, the curated `piModelMenu`, and Lattice-managed `piProviders`. The read/write **facade**; each field's validation lives next to the shape it produces — MCP in `mcp/settingsValidation.ts`, Pi providers (+ the `PiProvider`/`PiProviderModel` types) in `piProviderValidation.ts`, the concurrency clamp/bounds inline. Those validators + types are re-exported from `globalSettings.ts` for back-compat (piModels.ts + tests). See `globalSettings/CLAUDE.md`. Served by `routes/globalSettings.ts` (`GET`/`PATCH /api/global-settings`); a `PATCH` applies the new cap to the live queue via `setSpawnQueueSoftCap` and, when `piProviders` changed, reconciles `~/.pi/agent/models.json`.
- `spawnQueue.ts` + `spawnQueue/` — backend-side admission controller fronting every agent spawn. When concurrent spawns would exceed the machine-global `softCap` (from `globalSettings.json` → `maxConcurrentAgents`, default 24, env seed `LATTICE_MAX_CONCURRENT_AGENTS`) they are deferred in a durable queue rather than dropped; the terminal-server's `MAX_TERMINAL_SESSIONS` is now only a runaway backstop. `spawnQueue.ts` is the facade (`enqueueSpawn`/`cancelSpawn`/`notifySessionsFreed`/`startSpawnQueue`); `spawnQueue/` holds the pure accounting, drain, and `/sessions` poll loop. See its `CLAUDE.md`. Task-run durability across a restart = the persisted `Task.runQueued` flag + `recovery/queuedRunResume.ts` (which gives up after `Task.runFailureCount` exceeds a retry ceiling so a deterministically-broken run can't re-loop every boot). `taskSpawnEvents.ts` is the `task-spawned` / `task-spawn-failed` pub/sub: `task-spawned` delivers a queued task's pty to the frontend over `/ws/tasks` on success; `task-spawn-failed` carries a non-CAP spawn failure (worktree setup threw, terminal-server wedged) to the same channel so the UI can toast it (both queued thunks run detached, so the failure can't ride the HTTP response). The shared thunk body + failure handling live in `routes/tasks/queuedSpawn.ts` (`runSpawnThunk` / `reportSpawnFailure`). `taskActivityEvents.ts` is the analogous `task-activity` pub/sub: a running Claude worktree agent's PreToolUse/PostToolUse hooks POST `/api/tasks/:id/activity` (handled in `routes/tasks/activity.ts`, which maps the worktree path back to a project path), and the event fans out over `/ws/tasks` for the graph's focus beam. The sibling `routes/tasks/worktreeModified.ts` serves `GET /api/tasks/worktree-modified` (read-only worktree git diff per not-yet-merged task) for the `W` highlight, and `routes/tasks/colorSlot.ts` assigns each task's persistent palette slot (`Task.colorIndex`) at spawn. `agentSessions.ts` + `agentActivity.ts` extend the same node/beam visualization to Claude sessions that run *outside* a worktree (push / workflow step / post-merge hook): `agentSessions.ts` is a presence registry (register at spawn, unregister at the completion callback, served over `/ws/agent-sessions`), `agentActivity.ts` is event pub/sub, and `agentActivityTokens.ts` owns the HMAC token format used by `/api/agent-activity/:token` (`routes/agentActivity.ts`, fanned out as `agent-activity` on `/ws/tasks`). The shared `claudeHookBody.ts` parses Claude hook payloads and `activityHook.ts` decodes them into file activity or `SubagentStart`/`SubagentStop` lifecycle events, which drive the **subagent satellites** on the graph (a satellite spawns/stops on lifecycle events; a subagent's own tool-use carries `agent_id` so its focus beam hangs off the satellite). All three activity routes (`tasks/activity.ts`, `agentActivity.ts`, `projectClaude.ts`) and all hook-install sites (`claudeStopHook.ts` for worktree tasks + non-worktree sessions, `projectClaudeHooks.ts` for project-instrumented sessions) carry these. `agentQuiescence.ts` is a per-session `liveSubagents`/`lastSignalAt` tracker fed by the `wf:` **and** `pmh:` agent-activity hooks; it backs two Stop-hook quiescence gates — the **workflow-step** gate (`workflowRuns/stopHookGate.ts`) and the **post-merge-hook** gate (`postMergeHooks/stopHookGate.ts`) — each stopping a premature Claude `Stop` (those fire early/repeatedly once the agent uses subagents) from advancing a workflow step / finishing a post-merge hook while it is still running (the "steps sometimes run in parallel" bug, and its post-merge-hook analogue where a queued workflow overlapped the still-running hook agent). `projectClaudeHooks.ts` + `routes/projectClaude.ts` extend this to **any** Claude session working in an opened project (even ones Lattice didn't spawn): `projectClaudeHooks.ts` merge-installs activity hooks into the project's own `<project>/.claude/settings.local.json` (preserving the user's config, idempotent, removable — opt-out via `UserSettings.instrumentProjectClaudeSessions`), and `routes/projectClaude.ts` serves `POST /api/project-instrumentation` (install/remove on project open) + `POST /api/project-activity/:token` (the hook callback, keyed by Claude's `session_id`, reusing `agentSessions`/`agentActivity` with a per-entry idle TTL; `.lattice/`/`~/.lattice/` cwds are skipped to avoid double-counting Lattice-spawned sessions). `queuedCreateSession.ts` is the spawn-queue-gated drop-in for `proxyCreateSession`, used by every spawn site whose caller awaits the result (merge resolvers, post-merge hook, push, QA e2e run, prompt customization); task runs and workflow steps enqueue fire-and-forget instead. All eight agent-spawn sites are fronted by the queue.
- `terminalProxy.ts` / `terminal-server.ts` / `terminalServer/` / `terminal.ts` + `terminal/` — PTY lives in a detached child so main-server restarts don't kill running Claude sessions. `terminal-server.ts` is the detached entry point; `terminalServer/` holds its process guards, Express routes, `/ws/terminal` upgrade handling, parent-watch, and graceful shutdown wiring (see `terminalServer/CLAUDE.md` for the detached-process boundary). The main backend talks to it through `terminalServerClient.ts` — a barrel over `terminalServerClient/`: `sessions.ts` (best-effort probes/counting + kill by id/cwd, shared 3s timeout), `createSession.ts` (`POST /sessions` payload resolution, non-JSON respawn-and-retry, response parsing, 30s cap), `shutdown.ts` (`POST /shutdown`, 2s) — with `terminalServerLifecycle.ts` owning spawn/respawn/health (`BASE`, `ensureTerminalServer`) and `terminalProxy.ts` the public façade re-exporting both + `terminalWsRelay.ts`. `terminal.ts` is a re-export facade over `terminal/`: `sessionTypes.ts` (Session/CreateOpts/AttachOpts), `sessionStore.ts` (sessions map + `listSessions`), `launchContext.ts` (shell/cwd/size/project/env/docs setup), `broadcast.ts` + `sessionLifecycle.ts` (subscriber broadcast, pty onData/onExit, banner, initialCommand), `createSession.ts` (`pty.spawn` orchestration + `precreateSession`), `attach.ts` (`attachTerminal`, session_lost, resize-on-attach, WS message handling), `kill.ts` (`killSession`, `killSessionsByCwd`, post-kill `ensureClaudeConfigValid`). Add new files to `terminalFingerprint.ts`'s `FINGERPRINT_FILES` so byte changes still invalidate stale orphans.
- `processGuards.ts` — swallows node-pty's known Windows cleanup throw; every other uncaught exception/rejection is logged and then fails fast (exit 1) so a real bug can't leave the backend running in an undefined state. Regression-covered by `__tests__/processGuards.test.ts`.

## Key invariants

- **One active merge run per project** — in-process (mergeRuns.ts, second start returns 409) *and* cross-process (`projectRunLock.ts`).
- **Workflow runs survive a backend restart** — mirrored to `~/.lattice/per-project/<hash>/workflow-runs.json` and re-adopted on boot (`recovery/workflowRunResume.ts`). Agent-step ptys live in the detached terminal-server and survive, so re-adopting the run record is enough for the pending `/complete` to advance it; control steps are re-dispatched. Keep `restoreWorkflowRun` idempotent and the mirror current on every run mutation.
- **Merge runs survive a backend restart** — they execute in-process (so `tsc -w` + `node --watch`, or a crash, kills them), but `scripts/dev.mjs` defers restarts while a `run.lock` is held, and on boot `resumeInterruptedMergeRuns` restarts any run whose `run.lock` is stale. Net effect: a "merge all" runs to completion from one click. So keep the run re-runnable — `startMergeRun` must tolerate being invoked on a half-processed task set.
- **Per-task merge lock** (`mergeLocks.ts`) — manual /merge can't race the run worker.
- **Crash-safe ordering**: `updateTaskCrashSafe` writes disk before cache. Used for `ready_to_merge → qa` transitions.
- **Merge in worktree, not main** — see `worktree/merge.ts`. Main's tree only ever changes via fast-forward.
- **All project-repo git goes through `projectGit`** — never raw `exec('git', …, repoRoot)`. Worktree-side git stays on `exec` (disposable, and it needs the real `git merge` that `projectGit` forbids).
- **No `fs.rm({recursive})` on anything inside a project** — worktrees live outside the project tree; worktree teardown delegates the recursive delete to `git worktree remove`. One-off scratch cleanup (push / QA / post-merge hooks) is an intentional recursive delete, and it is bounded to `~/.lattice/per-project/<hash>/{push,qa,post-merge-hooks}/<id>/` with path + reparse-point guards.

## Type-check

`src/` is the source of truth; `dist/` is generated by `tsc` and should not be
edited. `npx tsc --noEmit` from `backend/`. Tests: `npm test` (node:test via
`tsx`, runs `src/__tests__/*.test.ts`).

`tsc` only emits `.js` for `.ts`. Non-TS runtime assets under `src/` (currently `workflowRuns/create-task-template.cjs`, read at boot by `renderHelperScript`, and `latticeApiDocs/LATTICE_API.template.md`, read by `latticeApiDocs.ts`) are copied into `dist/` by `scripts/copy-assets.mjs` — run from **both** `npm run build` (`tsc && node scripts/copy-assets.mjs`) and `npm run dev` (`scripts/dev.mjs` runs it right after the initial `tsc`). Add a new asset → add it to `copy-assets.mjs`'s list (one place, both paths). Forgetting this crashes the backend on boot with `ENOENT … dist/…`.

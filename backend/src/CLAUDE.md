# backend/src

Express server (`:5184`) plus a detached PTY subprocess on `:5185`.

## Layout

- `index.ts` — entry point. Installs `processGuards` first, then dynamically imports `server/startup.ts`.
- `server/` — backend bootstrap helpers: config/default root, Express app + route mounting + JSON error middleware, HTTP/WS server wiring, and startup ordering (`ensureTerminalServer` + `recoverOrphanedTasks` before listen, `resumeInterruptedMergeRuns` after listen).
- `recovery.ts` / `recovery/` — `recovery.ts` is the stable public shim; focused modules under `recovery/` handle boot recovery: restore tasks.json from backup → restore orphan working-tree snapshots → **`sweepOrphanedWorktrees`** (reclaim worktrees git tracks that no live task owns) → recover ready_to_merge tasks whose branch was deleted. Also exports **`resumeInterruptedMergeRuns(backendOrigin)`** (called from `server/startup.ts` *after* `listen`): a merge run executes in the backend process, so `tsc -w` + the dev restart loop will kill it whenever a merged task fast-forwards `main` with a `backend/src` change (or the run's working-tree snapshot churns an uncommitted `.ts` file) — this spots the stale `merge-run` `run.lock` that leaves behind and starts a fresh run for the remaining `ready_to_merge` tasks (idempotent on partial states). The dev runner *also* tries to avoid the restart in the first place (`scripts/dev.mjs` defers a restart while a `run.lock` is held); this is the backstop for when one happens anyway (or a real crash).
- `routes/` — one router per domain (tasks, mergeRuns, workflows, settings, terminals, health). Each is a `buildXRouter()` factory and is mounted from `server/app.ts`.
- `ws/` — single `upgrade` dispatcher in `wsServer.ts`, generic project-scoped helpers in `projectEndpoint.ts`, and endpoint-specific WSS factories under `ws/endpoints/`. Adding a WS endpoint = add an endpoint builder plus a route in `attachWebSockets`.
- `worktree/` — git-worktree subsystem (see its `CLAUDE.md`). The `worktree.ts` shim re-exports the public surface. Includes `projectGit` (whitelisted git wrapper for the project repo) and `gitBackup` (`git bundle` pre-run backup).
- `pushRuns.ts` / `pushRuns/` — one-off Claude sessions for the QA-lane Push button. Session scratch lives at `~/.lattice/per-project/<hash>/push/<id>/` (not `<project>/.lattice/`) and cleanup is guarded so recursive removal only targets that home-scoped root.
- `projectPath.ts` — `canonicalProjectPath`, `projectHash`, `latticeHomeDir`, `homeProjectDir`, `homeProjectScratchDir`, `homeWorktreesDir` — the single source of truth for per-project paths under `~/.lattice/`.
- `projectRunLock.ts` / `projectRunLock/` — cross-process per-project lock (`~/.lattice/per-project/<hash>/run.lock` = `{pid, hostname, startedAt, label}`, PID-liveness probe). Held for the duration of a merge run (`label: merge-run`) / manual `/merge` (`label: manual-merge`). The in-process guards (mergeRuns singleton, `mergeLocks`) don't see other Lattice processes; this does. `inspectProjectRunLock` reads it without acquiring — used by recovery's merge-run resume to spot an interrupted merge run, and by `scripts/dev.mjs` to know when to defer a restart. `projectRunLock.ts` is the public facade; the subfolder splits path construction, lockfile parsing, liveness checks, stale-lock stealing, acquisition, and release helpers.
- `tasks.ts` / `taskCache.ts` / `taskCache/` — `tasks.ts` and `taskCache.ts` are stable re-export shims; implementation lives in `taskCache/` (see its `CLAUDE.md`). It owns the in-memory per-project task cache, 100 ms debounced persistence, home-dir storage under `~/.lattice/per-project/<sha1(canonical-path)[:12]>/tasks.json`, `~/.lattice/projects.json` indexing, legacy in-project migration, and crash-safe updates that write disk before mutating cache.
- `workflows.ts` / `workflows/` — workflow definitions facade plus split types, normalization, and `WorkflowStore`. Uses `ProjectStateManager` while preserving `<project>/.lattice/workflows.json`, step normalization, and `(projectPath, workflows)` subscriber fan-out.
- `harnesses.ts` — shared backend vocabulary/helpers for agent harness strings (`claude` / `pi` / `codex`). Reuse this instead of open-coding harness unions or normalization.
- `workflowPromptCustomizations.ts` — creates `.lattice/workflow-prompt-customizations/<id>/` prompt-customization sessions, spawns the selected harness, and accepts the callback containing the revised prompt.
- `mergeRuns.ts` + `mergeRuns/` / `workflowRuns.ts` + `workflowRuns/` — sequential run engines. `mergeRuns/` holds state/preflight/per-target helpers (see its `CLAUDE.md`); the public singleton + worker loop stay in `mergeRuns.ts`. `mergeRuns` also: takes a `git bundle` backup pre-run, holds the cross-process run lock, and runs a circuit-breaker (`.git`-exists + HEAD-only-forward) between tasks that halts the whole run on a violation. Singleton WS subscribers (`subscribe`) for live event fan-out. The run lives in-process, so a backend restart kills it — but it's written to be safely **re-runnable**: `startMergeRun` re-scans `ready_to_merge` (incl. conflict-flagged) tasks and re-attempts each, and a half-done task (worktree merged but `main` not FF'd, finalize interrupted, …) is idempotent on retry. `recovery.ts`'s `resumeInterruptedMergeRuns` leans on this. `workflowRuns.ts` is a thin facade over the `workflowRuns/` submodules — see its `CLAUDE.md`.
- `terminalProxy.ts` / `terminal-server.ts` / `terminalServer/` / `terminal.ts` + `terminal/` — PTY lives in a detached child so main-server restarts don't kill running Claude sessions. `terminal-server.ts` is the detached entry point; `terminalServer/` holds its process guards, Express routes, `/ws/terminal` upgrade handling, and graceful shutdown wiring. `terminal.ts` is a re-export facade over `terminal/`: `sessionTypes.ts` (Session/CreateOpts/AttachOpts), `sessionStore.ts` (sessions map + `listSessions`), `launchContext.ts` (shell/cwd/size/project/env/docs setup), `broadcast.ts` + `sessionLifecycle.ts` (subscriber broadcast, pty onData/onExit, banner, initialCommand), `createSession.ts` (`pty.spawn` orchestration + `precreateSession`), `attach.ts` (`attachTerminal`, session_lost, resize-on-attach, WS message handling), `kill.ts` (`killSession`, `killSessionsByCwd`, post-kill `ensureClaudeConfigValid`). Add new files to `terminalFingerprint.ts`'s `FINGERPRINT_FILES` so byte changes still invalidate stale orphans.
- `processGuards.ts` — swallows node-pty's known Windows cleanup throw; everything else logs and continues.

## Key invariants

- **One active merge run per project** — in-process (mergeRuns.ts, second start returns 409) *and* cross-process (`projectRunLock.ts`).
- **Merge runs survive a backend restart** — they execute in-process (so `tsc -w` + `node --watch`, or a crash, kills them), but `scripts/dev.mjs` defers restarts while a `run.lock` is held, and on boot `resumeInterruptedMergeRuns` restarts any run whose `run.lock` is stale. Net effect: a "merge all" runs to completion from one click. So keep the run re-runnable — `startMergeRun` must tolerate being invoked on a half-processed task set.
- **Per-task merge lock** (`mergeLocks.ts`) — manual /merge can't race the run worker.
- **Crash-safe ordering**: `updateTaskCrashSafe` writes disk before cache. Used for `ready_to_merge → qa` transitions.
- **Merge in worktree, not main** — see `worktree/merge.ts`. Main's tree only ever changes via fast-forward.
- **All project-repo git goes through `projectGit`** — never raw `exec('git', …, repoRoot)`. Worktree-side git stays on `exec` (disposable, and it needs the real `git merge` that `projectGit` forbids).
- **No `fs.rm({recursive})` on anything inside a project** — worktrees live outside the project tree; worktree teardown delegates the recursive delete to `git worktree remove`. Push-run cleanup is an intentional recursive scratch delete, and it is bounded to `~/.lattice/per-project/<hash>/push/<id>/` with path + reparse-point guards.

## Type-check

`npx tsc --noEmit` from `backend/`. Tests: `npm test` (node:test, runs `src/__tests__/*.test.ts`).

`tsc` only emits `.js` for `.ts`. Non-TS runtime assets under `src/` (currently `workflowRuns/create-task-template.cjs`, read at boot by `renderHelperScript`, and `latticeApiDocs/LATTICE_API.template.md`, read by `latticeApiDocs.ts`) are copied into `dist/` by `scripts/copy-assets.mjs` — run from **both** `npm run build` (`tsc && node scripts/copy-assets.mjs`) and `npm run dev` (`scripts/dev.mjs` runs it right after the initial `tsc`). Add a new asset → add it to `copy-assets.mjs`'s list (one place, both paths). Forgetting this crashes the backend on boot with `ENOENT … dist/…`.
